# Desktop hosting account, authorization and payment

[简体中文](ACCOUNT-SERVICES.md) · **English**


`include/weapp/host_services.hpp` provides a standalone C++17 business adapter. It reuses the runtime
Shared account owner; `HostAccountManager` only packages account change, query, cancellation, retry and local data deletion.
The second set of epochs is not maintained. `HostApiContext` retains the complete runtime wire context, account epoch
and deadline use decimal strings and cannot be converted by JSON double.

<a id="接入顺序"></a>
## Access sequence

1. Construct application/account of `Config.host_services` from the host's trusted installation record.
`packRoot` must correspond to a verified package; the hash does not replace issuer authentication.
2. Create `HostServicesClient` and configure HTTPS origin and native-only host token provider.
provider selects credentials using the trusted application/account received with the request cannot hand over token to JS.
3. Wait for the asynchronous result of `prepare_configuration`, then configure and create the session. SDK does not pass blocking
UI callback fake synchronization `identity.getState`; the state before JS starts comes from the actual backend.
4. Create `HostServices`, configure `HostConsentPresenter::native(parent, status)` or your own
Native authorization presenter, finally `install(session)` before `load()`. Business `on_event` monitoring continues
receives its original event. No consent presenter does not register the interactive authorization capability; no payment channel does not register the payment capability.
5. After redeeming the login code, restoring the front desk, revoking the authorization or refreshing the token, first get
`current_context(context)`, then `refresh(context)`. Future is settled by owner `pump()`.
The old owner’s context is rejected before obtaining credentials or making a request, and the late result cannot update the new owner’s synchronization snapshot.

```cpp
HostBackendOptions options;
options.endpoint = "https://host-backend.example";
options.host_token = [accounts](const HostApiContext& context) {
  return accounts->bearer_for(context.application, context.account);
};
Status status;
auto backend = HostServicesClient::create(std::move(options), status);
// Handle status and await backend->prepare_configuration(trusted_configuration)
// on the host's async executor before creating/loading the Session.
```

SDK only calls the host entrance of the reference service: login code, application session check, identity status, information, authorization policy,
consent, mobile phone number, application exit and order launch. Independent app client secret, issuer secret,
The business app bearer and order amount remain in the backend; the SDK does not provide a guest entry for these credentials.
Select the request to carry `miniAppId/packRoot/expectedPrincipalId/expectedPrincipalEpoch` in its entirety.

<a id="网络与授权-ui"></a>
## Network and Authorization UI

macOS uses ephemeral `NSURLSession`, Windows uses `WinHTTP`, Linux uses 7.85+
`libcurl`; Linux builds without libcurl explicitly refuse to create backend clients. Requests are made by two workers
Executed, queue maximum 128 items, active work maximum 256 items; redirects, cookies and automatic host authentication turned off,
System certificate verification remains enabled, the response limit is 256 KiB, and the maximum single request is 15 seconds. Development HTTP only allows explicit
`127.0.0.1/localhost/[::1]` origin turned on. Cancel and interrupt the native request, the result is only in the owner pump
Workaround; Host credentials are not automatically attached to any applet network request.

Backend error supports string `error` and object `error`. Expose API fields by envelope,
envelope.details, error.details, and error are merged in order, and the subsequent non-null values take precedence;
`code/message/error/details` always belongs to container information and is not mixed with public fields.
`HostResult<T>::api_details` retains the original `errCode`, `errMsg` and public extension fields, independent of
`status` and `backend_code`; the new member is at the end, and the aggregate initialization of the existing three members maintains source compatibility.
The five types of container errors and their `ERR_*` form retain the original classification, and the identity or authorization invalid aliases are classified as
`permission_denied`, unknown backend classification is classified as `invalid_request`. callback, Promise,
Identity refresh, authorization and payment all go through the same field projection; backend raw errors are no longer overridden by SDK defaults.
`unsupported_capability` / `ERR_UNSUPPORTED_CAPABILITY` and `unsupported` belong to the same category;
The public code of JS is generated by the runtime according to the existing contract. Identity refreshes after the business has failed only try their best to update the snapshot,
The second refresh failure will not replace the original business error; the necessary refresh failure after the business is successful will still return the refresh error normally.

The native authorization UI is AppKit sheet, the Win32 window and GTK dialog belonging to the host HWND must be bound
Visible host parent. Display the application, purpose and permission version registered in the backend; confirm the information and mobile phone number separately.
Rejection is still written back to the backend, window closure/account-change cancellation does not imply consent. Custom presenter completion
Must and can only settle once. When receiving cancellation, close its UI and settle the cancellation.
The controlled presenter in the test only verifies the protocol and life cycle and cannot be accepted as the native UI.

`wx.getUserProfile` still must pass the facade's non-empty `desc` check; the purpose of native UI display comes from the backend
policy, not replaced by guest desc. `wx.getUserInfo` only reads existing authorizations. Mobile phone number returns to application scope
One-time code, routed into the internal host API through the real `getPhoneNumber` button, not exposed to the guest
`wx.getPhoneNumber`. `revoke(context, kind)` revokes one authorization category for the specified application/user and refreshes the snapshot.

After the application exits successfully, the runtime revokes all associated controllers of the application and rebuilds its JS owner;
Undo precedes the old JS continuation, the old logout callback/Promise does not enter the replacement owner. host from
The account switching event and query final state observation are completed, and the synchronized snapshot of the new entrance reflects that the app is not logged in. Other mini-programs
It is retained with the host account, and the backend’s existing separate profile/phone-number consent will not be automatically deleted when the application exits.

## Desktop Payment Boundary

`HostPaymentChannel` is the typed access boundary between the host’s official channel and the SDK. guest only passes `orderId`;
the SDK obtains a launch from the backend bound to the trusted application/account/epoch bound launch, rejecting guest payment signature.
The desktop only accepts `wechat-qr/alipay-qr` (native) or explicit channel corresponding
`wechat-h5/alipay-h5`(h5). APP and JSAPI parameters cannot be passed to the desktop channel and are not automatically converted.
Only one payment UI is allowed at the same time; selection is refused when channels support overlap.

The completion of channel `launch` uses `HostApiError`, and the original channel can be retained in `details` when it fails.
`errCode` (number or string), `errMsg` and public extension fields; the container is still responsible for outer error classification and calling
Context. completion must be in its own UI/task has terminated and released its resources before settling; success only represents the channel
Once the interaction is completed, it does not mean payment. QR checkouts can provide a clear "Done" button, but the button does not prove payment.
SDK polls again according to the same order
Backend, only the server `paid` returns `serverConfirmed:true` to JS. The wait limit can be configured as
1 second to 5 minutes, default 15 seconds; waiting timeout, closing and changing number only terminate the client waiting and do not cancel, refund or
Re-initiate deduction. The channel must respond to cancellation by stopping its own UI/wait and complete callback.
WeChat/Alipay product activation, QR/H5 Host presenter, fallback, and formal credentials are explicitly configured by the host.
The current delivery channel interface and strict server confirmation process; the built-in three-terminal formal QR/H5 display still needs to be accepted.

The local reference channel must also explicitly install the corresponding channel and open it
`allow_reference_payments`, only `reference/app/reference` is accepted and is never used for formal failure fallback.
The signature verification and order attribution of the reference service are still performed as usual and will not be registered as real merchant transactions.

Currently C++ `Session` and C session reuse the shared `HostAccountManager` of the runtime. Same
All controllers of `hostAppId` / `tenantId` share accounts for epoch; `switchAccount` immediately revokes the old
Identity, native device and GPU cleanup begins with the `revoking` event of `accountSwitch`. public controller
Remain stable, internal JS session, page stack and query parameters are rebuilt by runtime.

<a id="异步清理与身份快照"></a>
## Asynchronous Cleanup and Identity Snapshot

Asynchronous identity refresh requires the runtime to provide `hostServices.snapshotOwnerContext == "1.0"`;
SDK checks before initiating backend work, old runtime explicitly returns `ERR_UNSUPPORTED_CAPABILITY`.
`current_context` freezes the full application, account/epoch and internal sessions before requesting; `refresh`,
`revoke` and API callbacks inherit their original context and do not attach new owners to late results. The core will also verify
Package and full application information accepted. The old result after account change, application exit and reload with the same account returns `ERR_CANCELLED`.
The general snapshot command with context also requires this negotiation; snapshots generated synchronously by the existing owner thread can be omitted.
Successful snapshots will be merged and retained in the controller configuration, and will be replayed during preflight reconstruction. macOS When permission changes are queued
Freeze the owner together and submit it through `values` without placing the permission field at the top level of the command.

Call `set_account_cleanup_handler` before loading. The SDK first drains its own device and unbinds the GPU, and then
The UI thread that created the session calls the host hook once. hook returns
`std::shared_future<AccountCleanupResult>`, the host completes the remaining resource cleanup and
New identity prefetching; SDK’s `pump()` only performs non-blocking checks, and passes `sync_values` in its own thread
`prepareAccountHostServiceSnapshots` is submitted to the same operation, and then cleanup is confirmed.

```cpp
session->set_account_cleanup_handler([backend](const AccountCleanupContext& context) {
  // backend owns its credentials, cancellation and executor. It returns a
  // shared_future and never calls Session from a worker thread.
  return backend->drainAndPrepare(context.operation_id, context.application, context.account);
});
```

The synchronized identity snapshot is still provided by the host's real backend. Credentials are retained on the host; `sync_values` should not contain
Host token. Asynchronous results cannot be blocked on the UI thread with `wait()` / `get()`; deferred future is explicit
failed. The task of the old operation must first reach the final state before the hook of the latest operation can be started;
Old snapshots will not be submitted to the new owner. The error remains blocked and will be called after the host repairs the condition.
`retry_account_cleanup()`. Retrying does not restore the old identity.

Each time `revoking` replaces the SDK replay cache with the complete snapshot provided by the runtime, when this metadata is missing
Clear cache. The runtime only retains applet metadata and device snapshots: `getAccountInfoSync`,
`getSystemSetting`、`getDeviceInfo`、`getWindowInfo`、`getAppBaseInfo`、
`getSystemInfoSync`, `getBatteryInfoSync`; the identity status is reset to an unauthorized application of the host account
status, other custom snapshots are left blank. The new value of hook can only be integrated into the new baseline of this operation, omitting the value
Old user authorizations will not be inherited. The OS reservation list is maintained by the runtime, and the SDK does not create another divergent list.

`close()` returns `ERR_RESOURCE_CLEANUP_PENDING` when the started hook has not ended; persists
`pump()` will promote shutdown after the task ends. Blockage continues when cleanup fails, errors are reported via events and can be made explicit
Try again. The close request will not start a new account JS due to successful cleanup. The host should always complete the tasks issued by itself.
Then wait for `Closed` before destroying the controller.

After installing the identity adapter, when changing the number, first cancel and empty the adapter's request, subscriptions and authorization/payment UI, and then
Run the existing host cleanup hook. The hook should install the new host credentials in its own task; after the hook is successful, the SDK
Automatically request the real backend status of the new account, bind it to the same operation, submit it, and then ACK. Backend prefetch failed
Also remain blocked and require explicit retry; log out of the host account and use null principal, prepare for confirmed non-login
Snapshot, does not call the old bearer, and does not generate a sandbox account. If the backend needs to revoke the host session or delete the account,
The host is still responsible for performing the actual backend actions; local data deletion receipts are not proof of backend deletion.

The C API provides the corresponding `weapp_desktop_session_set_account_cleanup_handler`. callback borrow
application/account field and gets an own completion. call
`weapp_desktop_account_cleanup_complete(&completion, sync_values, error_code,
error_message, &error)` only fulfills the promise and can be called from other threads; it does not enter the runtime.
Each completion must and can only be settled once, and the pointer will be empty after successful consumption. Cancellations must also be settled in error.
