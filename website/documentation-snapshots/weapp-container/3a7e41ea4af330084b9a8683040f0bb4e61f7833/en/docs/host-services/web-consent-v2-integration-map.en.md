**Shared Domain, Object Ownership, and Minimum Host Interface**

Durable domain `D = [hostAppId, tenantId, publisherId, principalId, appId, environment]`; each kind's `C = [D, profile|phone]`. `version`, `packRoot`, epoch, sessionId do not enter the persistent consent key; trusted installation remains verified on each execution. Execution binding `E` includes D, epoch, actual sessionId, and owner/incarnation separately. User switching number increments epoch, retires old E; new epoch for the same user can read still-valid durable grant, old challenge/code/call cannot cross over. Application exit retains consent; removal of user only clears the corresponding durable domain.

All client instances, valid upgrade versions, and direct/Worker owners within the same host must obtain the same coordinator; do not create a separate map for each createReferenceIdentityClient, manager, or URL copy. It is recommended that the host root inject a protocol-constrained shared object; if the strict v2 version is missing, immediately reject. If multiple managers are allowed, they must also use the same host/tenant root registry. Do not terminate the same persistent domain via endpoint URL, package version, or new epoch. Relying solely on module-level variables will still result in a second set of state due to repeated module URLs or different bundle versions. In a strict domain, if an existing v1/old runtime owner cannot participate in a fence, its strict admission must be rejected or retirement/reconstruction must be completed first; it must not retain a cached disclosure queue, omit from the ACK set, and then claim "all clients have withdrawn." Legacy fixtures may continue to run their own explicit legacy apps, but do not receive new withdrawal guarantees.

The minimum coordinator semantics can be grouped into five categories of interfaces, with specific naming to be finalized together with the runtime wire:

1. `attachOwner(E, requirements, nativeLane)` returns a bounded registration; the owner must be installed and ACK the current authority before app.init. `detachOwner` only releases this E, without deleting C's revision. close waits for the fence/mailbox termination of this owner, without waiting for the closure of all owners in the host.
2. `capture(C,E)` / `assertCurrent(ticket)` : the ticket stores the kind-local generation, backend canonical revision, authority notification generation, and owner incarnation; it does not store bearer/challenge. The stamp of a native pending call must be exported by a trusted runtime context/host admission and cannot be generated from the payload.
3. `observeState(E,envelope)` : validates v2 identityProtocol, per-kind revisions, expiresIn, and whitelisted public state; compares revisions as BigInt and maintains local expiry using a monotonic clock; a regular refresh cannot increment the authority notification generation, nor can it override a later revoked one. Version conflicts are limited to a finite number of re-reads within the original deadline.
4. `beginRevoke(C)` / `commitRevoke(operation,backendReceipt)` : upon calling begin, synchronously increments the local kind generation, invalidates all previous popups/requests/queued items; installs a fence to all associated native owners; then submits the backend revoke. future succeeds only after actual owner ACK, backend submission, and projection completion; partial failures retain blocked/pending/failed states and retry phases, and old tickets cannot be re-enabled.
5. `adoptOwnGrant(ticket,decisionReceipt)` : adopts a new revision only if the generation has not changed, the decisionId/challenge corresponds to the current operation, and the receipt revision is the current value recognized by the coordinator. It cannot override the expected value upon encountering a 2xx response, nor can it treat a revoked old grant receipt as a regular refresh.

reference provider current public handler name can be retained. A new host-only prepare/read authority envelope and revoke/refresh operation must be added, allowing BrowserHostServices to access internal revisions, while guest `getState` continues to see only four boolean fields, an opaque authorizationVersion, and authorized public userInfo. Independent `getStateEnvelope/prepare/revoke` methods or equivalent type-constrained protocols can be used; do not inject internal fields into userInfo or return raw backend objects to all callers. Under strict mode, the userInfo whitelist for BrowserHostServices should also be tightened: currently, the userInfo from custom providers is fully copied via safeValue, whereas only the reference provider performs nickName/avatarUrl projections.

The account manager's owner factory should replay the same coordinator, requirements, and provider configuration, rather than serializing the coordinator into launchOptions. The existing boundary of `replace()`'s old owner drain → factory → start → waitForPresentation continues to be used; if either factory/start fails, the operation remains blocked. same-user refreshCredentials does not restart and does not delete consent. logout only retires the app owner; the instance count of the current reference `change:logout` cannot be directly changed to a persistent profile/phone revoke.

**The Required Contract for Runtime and Rebuilding**

Retain base hostServices 1.0 and existing C ABI; add precise `consentRevocation:1.0` capability and `hostServices.requirements:{consentRevocation:"1.0"}` (naming follows existing design, schema must still be frozen). Additionally define: initial per-kind authority, call context stamp, completion witness, authority vector for snapshot/event, and operationId/stage/final state/ACK for host-only apply/fence commands. Do not disguise authority updates as old `native.snapshots`.

Need to simultaneously change HostServicesConfig, normalize/configure, HostApiCallContext, HostApiEvent/Completion, WASM host exports and host_services_protocol_json; both Web direct and Worker adapter perform validation and pass through. The old Completion's deny_unknown_fields implies that we cannot first send a new witness today and then pretend the old runtime accepted the fence. The snapshot native provider must also verify the current authority during synchronous reads and cannot rely on waiting for asynchronous UI/HTTP to achieve synchronous state.

The `nativeHostServices` allowlist of Worker, the WorkerRuntime execute switch, WorkerHostServicesTransport, and the load/activate handshake must be updated together. New commands must go through the trusted native lane and must not be exposed to `session.request`/guest bridge. Command cancellation does not imply that the underlying fence was not executed; retain actual final, allow rollback on failure with visibility and retryability, and close should not consume operations not yet ACKed. Overflow of bounded queues must not discard safe fences or unique failure terminal states.

Each Worker has its own independent WASM instance/memory, and Rust statics cannot be treated as shared authorization tables across Workers. A shared coordinator maintains D/C in the host realm and then installs and waits for a local runtime barrier for each real owner. Sync JS already running in a Worker will not automatically stop due to a map increment in the main realm; a clear linearization point for revocation and a final verification mechanism for native.complete/JS microtask completion are required. If the requirement is that "after the same sync moment returned by beginRevoke, no other Worker's currently executing old JS should be able to see any data," the existing asynchronous postMessage cannot prove this, requiring additional shared authority/scheduling barriers design—only writing two Maps is insufficient. At least, it cannot be claimed that revocation future is successful before all ACKs have arrived.

Preloading has an isolated window: services.configure reads old state → battery/permission awaits → returns captured config → session.load downloads/initializes → Worker configure → app.init can synchronously read old userInfo. Activating/refreshing after load returns is too late. Candidate registration should happen before start, carrying the current stamp and enabling reload/thermal update replay requirements; if necessary, split native inert-load and app.init into two explicit admission phases, or use a verified equivalent barrier. Reconstruction must not drop requirements or reset the latest fence. When old owner cleanup fails, new owner remains blocked; old snapshot is not restored.

Each sensitive boundary should at least be: entry/native request enqueued; after hostToken await; after fetch/each reader.read; after policy and UI await; before and after grant send and receipt; after disclose/state await; before snapshot application; after handler successful continuation; when completion/event/snapshot is enqueued to host; after each drain await; after native command is actually executed; after Rust complete/phone/button/event; and finally, the real JS disclosure microtask. callback option getter, toJSON, success/complete callback re-entry and microtask must not be skipped. `__container_resolve_api` must preemptively remove pending behavior with the new single-batch settlement state, and cannot fence failure by both failing to find pending and not releasing budget.

Must define a single, irreversible point for settlement: after the success callback has read the materials, it cannot claim revocation to make it "never have occurred"; when a revoke is initiated within the success callback, the subsequent rules for complete/Promise must be frozen and tested, and it must not simultaneously return a success and then append a failure, or incorrectly resurrect the original Promise. Any living owner that has not yet entered a successful disclosure must fail → complete → Promise rejection in a single, final step; if the owner has retired, the old JS must be prohibited along the existing closure path. The current controller.signal aborted branch only applies to the latter case and cannot override the former.

UI and actual resource termination of HTTP also need independent recording: the existing wait(promptPromise, signal) only causes waiters to reject, without proving that the native prompt has been dismissed. A strict presenter should provide a real closeable and waitable receipt (or an equivalent constrained interface), and close/revoke should track this receipt, retaining retry on failure; it must not discard old UI promises that are permanently pending and consider them cleaned up.
