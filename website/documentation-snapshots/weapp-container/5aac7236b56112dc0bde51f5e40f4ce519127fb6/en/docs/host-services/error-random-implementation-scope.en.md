# Scope of Implementation for Random Values and Private Error Listeners

[简体中文](error-random-implementation-scope.md) · **English**

wx.getRandomValues is held by Session, invoking the operating system's CSPRNG via getrandom; WASM builds use the Web Crypto backend. Guest, configurable provider, and object's toJSON cannot provide random bytes. Length accepts only integers in the range 0..1048576; the JavaScript facade reads the retained structured options as a regular property once, and the callback invocation returns void, while without a callback it returns a Promise with a true ArrayBuffer result. Exceptions in callbacks are still processed by complete and routed into a private error reporting channel; internal Promise failures delivered via fail are not consumed. Both runtime entry points share manifest/host admission, cancellation, timeout, and termination checks; entropy source failures do not return the allocated buffer.

This batch simultaneously fixes the fork in capability publishing and invocation admission: effective_capability_with_provider is uniformly computed, and the entire capability table reuses a single provider inventory snapshot. The existing manifest/runtime registered host keys, route/error capability limits, alias, identity/account gatekeeping are retained. Equivalent conclusions apply only to published keys within the same stable snapshot and cannot be used to infer arbitrary canIUse strings. Configurable providers cannot take over or disable runtime entropy sources; manifest and trusted host policies may still reject calls.

wx.onError/offError uses a shared lexical private hub. A regular host registry cannot override these functions or obtain access through their counterparts; native holds the reporter and termination entry, while guest modification of diagnostic aliases does not alter the holder. on/off each have independent access, preserving the previous on-only manifest semantics; offError removes the function exactly or clears it with no parameters, returning void, and during delivery, handles additions and deletions as snapshots. A trusted on cancellation clears subscriptions, cleans up upon termination, and cannot re-register using the old function; off cancellation does not remove entries even if access to on is still granted.

The scope of completion covers only unsubscribing from offError. onError still lacks a fixed ListenerError payload projection, complete uncaught exception origin, App.onError dispatch, and own-data-only stack normalization; these remain partially unaddressed. UserCryptoManager.getRandomValues continues to be a standalone host capability. This batch does not infer that these gaps have been closed based on RNG or offError completion.
