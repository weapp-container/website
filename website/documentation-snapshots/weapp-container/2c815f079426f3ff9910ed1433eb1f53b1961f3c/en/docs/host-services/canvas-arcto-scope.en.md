# CanvasContext.arcTo Implementation Scope

[简体中文](canvas-arcto-scope.md) · **English**


Product submission `2b36a3d1374f2f35147177bf2804d7b3f8b0d281` implements legacy `CanvasContext.arcTo(x1, y1, x2, y2, radius)` within existing Canvas transaction boundaries. Fixes the requirement for five mandatory number parameters, returning void. JS copies the parameters into a bounded command queue; the complete batch pre-check completes decoding, geometry, and work budget validation before allowing any rendering backend to publish pixels.

Prepass restores current path endpoints at construction time using CTM, computes two tangent points in f64, and converts them once into three transformed points with positive weights for a rational quadratic curve. The portable backend uses bounded homogeneous subdivision, while native Skia uses conic_to on the same curve; neither path separately recomputes the center or tangents. Large radii are not truncated to control segments, and the endpoint is the second tangent point, with no automatic connection to the second control point. Empty paths, zero radii, coincident points, and collinear cases are degraded to moveTo or lineTo via recorded branches. closePath, consecutive arcTo, transformations, clip, draw reset, and reserve replay reuse existing state boundaries.

All seven ends remain **Partial**. Input and storage are still constrained by finite-f32 range and precision limits, with potential underflow for extremely small positive radii; branches requiring inverse transformations reject singular CTMs; curve weights must be representable positive numbers, and subdivision depth along with existing geometry, rendering, and byte budget constraints limit parameter ranges. Negative radius rejection is a defined container policy, and there is no fixed behavior for WeChat 3.17.3 errors or complete raster consistency proof. Existing clip edge discrepancies have also not been resolved in this batch.
